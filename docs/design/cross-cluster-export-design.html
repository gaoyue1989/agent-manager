OAF 跨集群导出发布设计

测试环境导出交付包 + 镜像直推指定仓库 · ITSM 审批 · 生产 Helm 部署
状态：设计定稿 v1（2026-10-29，评审决议齐备，未实施） · 改动落点：backend 新增导出链路 + 新业务 chart oaf-agent + 运维侧默认配置页，测试集群发布链路零改动
正文（事实源）：docs/design/cross-cluster-export-design.md · 样例服务：差旅助手 travel-agent（工作空间 ws-3f9a21c4）

1. 决议记录（2026-10-29）

#议题决议
①生产密钥注入通道暂不做占位符脱敏：敏感值明文写入 values 文件、经文件代入部署；values 随 ITSM 工单按密级流转 敏感
②生产 Helm 部署接口形态复用生产侧已有 HTTP Helm 部署接口，平台不重建部署能力 外部已有
③镜像同步方式不引入镜像同步服务：backend 构建后直推指定镜像仓库，生产侧自己拉取生产同步镜像 直推
④生产 A2A 服务目录登记走另外流程处理，本期不涉及 范围外

背景：现发布链路隐含「backend 与业务集群同处一个 K8s」——配置包存共享 PVC、backend 直构 Deployment/Service/Ingress、包 subPath 挂 /config。测试环境定稿的 agent 无法交付到另一个 K8s 集群；生产环境没有平台 backend，配置、镜像、运行时环境必须随交付物自带；且 MCP 地址、模型网关、密钥等跨环境天然不同，需要一次受控的「导出时重配置」。

2. 目标与非目标

目标：

  • 用户侧导出发布页（测试 Console）：服务详情进入，提供配置包更新、版本查看、生产 env、模型/沙箱配置：
    ① 配置包更新 = 文本直改——包文件树（AGENTS.md / skills 只读）+ 纯文本编辑器（复用 package-online-edit 思路），保存即打发布标记（{包版本}-e{序号}）并把文件快照（path → content + checksum）写入发布标记表，构建 OAF 镜像只认该标记；
    ② 生产 env 可添加 / 编辑 / 删除服务专属键，运行时默认来源的行锁定（只能由运维在配置管理改默认）；
    ③ 模型 / 沙箱按模板展示全量参数（LLM 10 键 / Sandbox 6 键，与 platformconfig/template.go 同源），默认锁定。
    确认后 backend 生成 2 类交付物：OAF 配置镜像（构建后直推指定仓库）+ values 文件（随 manifest 提交 ITSM）。
  • 运维侧工作空间运行时默认配置：按工作空间维护 MySQL / Redis / OTel / 沙箱 / 镜像仓库 / 路由默认值，作为导出页预填与 values 组装来源。
  • 审批与部署：values + manifest 作 ITSM 附件审批；通过后调用已有 HTTP 部署接口，用 4 件套完成跨集群部署。
  • 测试集群零改动：现有发布链路（PVC 直挂、backend 构造业务资源）不变，导出是新增旁路能力。

非目标（本期不做）：生产侧平台 backend 与服务目录登记（决议 ④）；values 占位符脱敏（决议 ①，v2 视合规要求）；单集群发布链路与 PVC 挂载方式的任何变更；MCP export_service 对话式导出（v2）；ITSM / 部署回调自动化（v2）。

3. 总体流程

要点：构建与直推不写测试集群任何 K8s 资源；生产部署不经平台 backend 进程 「配置包更新」以发布标记冻结（快照落表），构建 OAF 镜像只认标记；values 不携带 MCP 覆盖段

4. 交付物规范（生产侧 4 件套）

交付物版本来源流转通道说明
oaf-agent chart固定版本（随平台迭代，如 0.1.0）制品库 / 离线包新业务 chart，与控制面 chart oaf-platform 分离，只描述单个业务 agent 运行时（§6）
基础镜像 agent-framework:agentscope-Xvalues 指定（运维白名单内选择）backend 直推指定仓库Java 运行时，/config 为配置挂载点（镜像已定义 VOLUME）
OAF 配置镜像 oaf-{k8s名}:{包版本}-e{导出序号}本次导出构建，digest 固定backend 构建后直推busybox 基底 + 配置层，labels 记录 slug/version/checksum/export-id（§5）
values.yaml + manifest.json导出单生成ITSM 审批附件敏感值明文写入 values（决议 ①），按密级随工单流转；manifest 用于审计与一致性校验（§7、§12）

5. OAF 镜像构建方案

内容：OAF 包目录（AGENTS.md / mcp-configs/ / skills/ / versions/…）打 tar 层，包内挂载点 /oaf；基底 busybox:1.36，保证 initContainer 在镜像内执行 sh -c "cp -a /oaf/. /config/" 可用。

构建与推送在 backend 进程内用 google/go-containerregistry 的 remote.Write 完成：OAF 镜像是纯数据镜像（KB~MB 级），该方式无 docker 依赖、无特权、同 tag 内容寻址可幂等重推；不引入 Kaniko（需特权与 RBAC，对配置镜像过重）。

方式依赖特权适用性
go-containerregistry remote.Write（选定）backend 引入一个 Go 库无纯数据镜像直推，进程内完成，幂等
Kaniko Job（否决）集群内 Job + RBAC需要特权运行时通用镜像构建，对配置镜像过重
  • 构建输入：导出单当前生效的发布标记（export_package_marks 快照，含文件树 JSON 与 checksum）；无标记不可构建，标记不可修改（改则生成新标记）。
  • tag 规则：{指定registry}/{namespace}/oaf-{k8s名}:{包版本}-e{导出序号}；构建完成后 digest 记录进导出单，部署前可按 digest 校验镜像就绪。
  • 推送凭证：来自工作空间运行时默认配置的 registry 组（§10），凭证存平台 Secret，不进任何导出产物。

6. 业务 chart：oaf-agent

与控制面 chart charts/oaf-platform（backend/frontend/router 自举）完全分离，新增 charts/oaf-agent，只渲染单个业务 agent 运行时，交付时固定版本。模板清单：deployment（initContainer + probes）、service、ingress（router/host 双模式，语义对齐 INGRESS_HOST_SUFFIX）、configmap / secret（envFrom 两源，对齐平台既有 per-service CM + Secret 模式）、mysql 建库 hook Job（可选）、serviceaccount。

initContainers:
  - name: inject-oaf
    image: {{ .Values.image.oaf }}            # busybox 基底的 OAF 配置镜像
    command: ["sh", "-c", "cp -a /oaf/. /config/"]
    volumeMounts:
      - { name: config, mountPath: /config }
containers:
  - name: agent
    image: {{ .Values.image.base }}           # agent-framework 基础镜像
    envFrom:
      - configMapRef: { name: {{ include "oaf-agent.fullname" . }}-env }
      - secretRef:    { name: {{ include "oaf-agent.fullname" . }}-env-secret }
    volumeMounts:
      - { name: config, mountPath: /config, readOnly: true }
volumes:
  - name: config
    emptyDir: {}    # 只读配置副本，Pod 重建即恢复，符合原则二（可丢弃/可重建）
  • initContainer 替代单集群的 PVC subPath 挂载——生产环境无共享 PVC 依赖，配置随镜像分发；
  • checkpoint 库名沿用 issue #142 派生规则 {基库}_{k8s名}（如 oaf_checkpoint_travel_agent），由 hook Job 幂等建库（CREATE DATABASE IF NOT EXISTS）或运维预建；
  • 默认 replicas >= 2、无 sessionAffinity，多副本横向扩展语义与单集群一致；
  • 自包含性（4 件套可独立部署，v1 验收前提）：chart 不硬编码 namespace（release 名与 -n 由部署方指定）、不引用平台任何对象（共享 PVC platform-data / platform-router / platform backend / platform_config）；MySQL/Redis/OTel/沙箱地址、imagePullSecrets、路由 host 全部来自 values——满足后在任一全新 namespace 仅凭 4 件套即可部署成功（见 §13 DoD）。

7. values 组装

7.1 四层合并（优先级从低到高）

层来源典型内容覆盖关系
L0 chart 默认chart 内置 values.yaml资源模板默认值、健康检查被上层覆盖
L1 工作空间运行时默认工作空间配置管理（/config/*，运维维护，§10）MySQL/Redis/OTel/沙箱/模型全量参数、registry、路由模式导出页锁定（仅运维可改默认）
L2 用户导出覆盖导出发布页表单包内 MCP 生产地址改写（进包）、服务专属新增 env 键（如 MCP token）、部署参数仅新增，不覆盖 L1 键
L3 平台生成导出单镜像引用与 digest、保留键（AGENT_CONFIG_DIR 等）、派生键（JDBC 库名 / Redis 前缀）、版本与审计标签不可覆盖

7.2 敏感值规则（决议 ①：文件代入）

敏感键清单与平台既有 sensitiveKeys 一致（LLM_API_KEY / CHECKPOINT_PASSWORD / AGENT_REDIS_URL / OPENSANDBOX_API_KEY 等），渲染进 values 的 secretEnv 段，由 chart 渲染为服务 Secret。v1 不做占位符脱敏：敏感值明文写入 values 文件、经文件代入部署；values 随 ITSM 工单按密级流转，文件保管由审批流程约束，平台侧下载记录审计（§12）。如后续合规提出脱敏要求，v2 在渲染层引入占位符机制，不改 API 形状。

包内敏感值统一以 ${ENV_VAR} 占位引用（如 MCP auth.token: ${MCP_FLIGHT_TOKEN}），跨环境只改 connection.url 等非敏感项——改完的包直接固化为 OAF 镜像，敏感值经 env/Secret 注入。

8. 数据模型与状态机（backend 新增）

新表随 backend 现有 GORM AutoMigrate 机制创建（与 users/workspaces 同模式）；agent-framework 零改动，不涉及 Flyway。

// 导出单：一次跨集群交付的载体
type ExportOrderEntity struct {
    ID               uint64
    ServiceID        uint64 `gorm:"index"`
    WorkspaceID      uint64 `gorm:"index"`
    SourcePackageID  uint64 // 导出时的源包
    ExportPackageID  uint64 // 在线编辑派生的新包（复用 package-online-edit 的 copy-on-write 链）
    ChartVersion     string
    BaseImage        string
    OafImageRef      string
    OafImageDigest   string
    ValuesYAML       string `gorm:"type:mediumtext"` // 渲染产物（含明文敏感值，接口层不做明文回显，仅文件下载）
    ManifestJSON     string `gorm:"type:json"`
    Status           string // draft/building/built/approving/approved/deploying/deployed/failed/cancelled
    ItsmTicketID     string
    Error            string
    CreatedBy        string
    CreatedAt        time.Time
    UpdatedAt        time.Time
}
// 索引：(workspace_id, status)

// 发布标记：导出级包编辑的快照（文本直改 → 打标记 → 落表 → 构建固化）
type ExportPackageMarkEntity struct {
    ID             uint64
    ServiceID      uint64 `gorm:"index"`
    WorkspaceID    uint64 `gorm:"index"`
    ExportOrderID  uint64 `gorm:"index"` // 0 = 尚未挂到导出单（草稿标记）
    Marker         string `gorm:"size:64;uniqueIndex"` // {包版本}-e{序号}，与 OAF 镜像 tag 对应
    PackageVersion string
    FilesJSON      string `gorm:"type:mediumtext"` // 文件树快照：path → content
    FileCount      int
    Checksum       string // 快照内容 sha256
    Status         string // frozen（已冻结，可构建）
    CreatedBy      string
    CreatedAt      time.Time
}

// 工作空间运行时默认配置（运维侧维护，导出页预填来源）
type WorkspaceRuntimeDefaultEntity struct {
    ID          uint64
    WorkspaceID uint64 `gorm:"uniqueIndex:uk_ws_runtime_default"`
    EnvKey      string `gorm:"size:128;uniqueIndex:uk_ws_runtime_default"`
    Value       string `gorm:"type:text"`
    Sensitive   bool   // 敏感键：接口回显掩码，仅渲染进 values secretEnv
    Category    string // mysql|redis|otel|sandbox|llm|registry|routing
    UpdatedBy   string
    CreatedAt   time.Time
    UpdatedAt   time.Time
}
draft → building → built → approving(ITSM) → approved → deploying → deployed
任意态可入 failed / cancelled

发布标记是 OAF 镜像构建的唯一输入：保存即冻结快照（FilesJSON + checksum），不可修改（改动生成新标记）；导出单创建必须携带 marker。

v1 中 approving → approved → deploying 由运维在平台人工推进（或脚本回填），v2 接 ITSM / 部署回调自动化。

9. API 设计（console JWT 之下）

Method · Path说明
GET /api/v1/services/:id/export/package包文件树与文本内容（AGENTS.md / skills 只读项标注）
PUT /api/v1/services/:id/export/package/file保存单文件文本修改（写编辑草稿，不冻结）

GET /api/v1/exports/:id导出单状态与详情（构建进度）

POST /api/v1/exports/:id/status人工推进状态（v1：approving / approved / deploying），记录操作人与 ITSM 单号
GET|PUT /api/v1/workspaces/:id/config/runtime-defaults运行时默认 env（分类键值，敏感掩码；导出页锁定来源）
GET|PUT /api/v1/workspaces/:id/config/mcp-connectorsMCP 连接器模板（connection / auth / permissions / 工具子集）
GET|PUT /api/v1/workspaces/:id/config/templates/:group模型 / 沙箱参数模板（llm / sandbox，复用 platformconfig 模板驱动）
GET|PUT /api/v1/workspaces/:id/config/registry仓库 / 拉取凭证 / 路由 / 镜像白名单

权限口径：导出发起要求 workspace 成员（与 services 归属校验同模式）；runtime-defaults 仅 workspace owner 与平台 admin；导出单可见性跟随 workspace。

生产部署不新增平台能力：审批通过后由运维/流程调用已有 HTTP Helm 部署接口提交 4 件套（chart + values 文件，镜像按 values 引用从指定仓库拉取）。镜像拉取前可按 digest 校验就绪。

10. 运维侧：工作空间配置管理（API + 页面重设计）

页面：控制台（运维视角）→ 工作空间 → 配置管理，页签 = 运行时默认 / MCP 连接器模板 / 模型参数 / 沙箱参数 / 仓库与路由 / API。统一入口管理导出所需的全部默认值；导出发布页全部继承本页，且默认值在导出页锁定——单次导出不能悄悄改基线，要改只能由运维在此修改（留审计）。与 platform_config（平台级、全服务表单默认）的区别：本模块 per-workspace、面向生产导出；测试集群「平台默认配置不经 envFrom 注入、仅表单预填」的语义不变。变更审计复用 platform_config_events 思路；导出页对新增键与 MCP 改写留痕，默认值本身不可在导出页修改。

参数模板与 backend/internal/service/platformconfig/template.go 同源（模板驱动表单 / 敏感路由 / 掩码输出）：LLM 组 10 键、Sandbox 组 6 键；SANDBOX_ENABLED 刻意排除（agent-framework 三层裁决：env 显式存在 > OAF 包 frontmatter > 默认 false，进默认配置会让包级沙箱声明永久失效）。字段分组：

11. 架构强约束核对

原则一（backend 是控制面）

  • 导出链路对测试业务集群只读（读包/env），构建与直推指定镜像仓库发生在 backend 进程 + 仓库侧，不写任何业务 K8s 资源；
  • 无启动期 reconcile、无后台批量迁移、无 ownerReferences / finalizer；
  • 生产部署走已有 HTTP 部署接口，不经平台 backend 进程；生产业务运行时不依赖 backend（env 经 chart 渲染的 CM/Secret envFrom 常驻、配置经镜像 + initContainer 自带、流量经 Ingress 直连）。

原则二（agent-framework 是业务面）

  • chart 无本地有状态：/config 为 emptyDir 只读副本（每次 Pod 重建即恢复，可丢弃/可重建）；checkpoint / Redis / OTel 全部指向生产共享存储；
  • 默认 replicas ≥ 2、无 sessionAffinity，任意请求可落任意副本；
  • 多服务隔离沿用 per-service 派生：checkpoint 库 {基库}_{k8s名}（幂等建库 hook）、Redis 前缀 {k8s名}:，与 issue #142 规则一致。

12. 安全与审计

  1. 敏感键路由：沿用 platformconfig 模板 sensitiveKeys 清单，values 中落 secretEnv 段（渲染为服务 Secret），普通键落 env 段（ConfigMap）；
  2. 明文 values 的边界（决议 ① 接受的代价）：values 含明文敏感值，仅经 ITSM 密级流转与平台下载（下载写审计日志：操作人 / 时间 / 导出单号）；导出单详情接口对 values_yaml 不做明文回显，只提供文件下载；
  3. 推送凭证：registry 推送凭证存平台 Secret，注入 backend 进程 env，不进导出单、values、manifest 任何产物；
  4. 包内密钥：OAF 包配置文件一律 ${ENV_VAR} 占位引用密钥，包本身可入库、可构建镜像、不携带明文；
  5. manifest 审计链：导出单号 ↔ 包 checksum ↔ 镜像 digest ↔ ITSM 工单号四方关联，生产侧可校验「部署的 values 就是审批的那份」。

13. 实施分期

阶段内容
v1 MVP① workspace_runtime_defaults 表 + CRUD API + 运维侧页面；② 导出发布页（前端）+ export/preview / POST export API + 导出单状态机；③ go-containerregistry 构建并直推指定镜像仓库；④ values（四层合并 + 明文 secretEnv）/ manifest 渲染与下载；⑤ 新 chart charts/oaf-agent（initContainer / 双模式 ingress / mysql hook）；⑥ 人工状态推进；审批通过后人工调用已有 HTTP 部署接口
