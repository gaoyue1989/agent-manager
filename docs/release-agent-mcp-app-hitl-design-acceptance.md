### 0.3 本轮发现并修复的缺陷

1. **部署配置短路确认**：运行中的发布助手包使用 `permission.mode: bypass` + `permissions.read_only: true` + `publish_service: allow`，受控写工具直接执行。已改为 `mode: default` 与五 `ask`/其余 `allow`，并在实例日志确认注册 12 个平台工具后复测弹卡。
2. **历史漏匹配导致刷新丢卡**：`ConfirmContextStore.findPending` 只匹配裸会话 ID 或 `:` 后缀，而运行时保存键为 `tenant__sessionId`（`makeThreadId` 用 `__`）。已补 `__` 后缀并改字面后缀匹配，避免 `_`/`%` 被当作 LIKE 通配符；新增真实 MySQL 集成测试。
3. **缺失 `confirmed` 被当作批准**：`buildResumeMsg` 原为 `!(obj instanceof Boolean b) || b`。已改为仅 `Boolean.TRUE.equals` 批准，并先用测试复现（expected false / actual true）再修复。
4. **前端推测式重建已撤回**：曾试图从历史悬空 `tool_calls` 重建待确认卡，会把已消费的调用重新显示为待确认，已回退为只读后端 `pendingConfirm`。

## 1. 目标与边界

### 1.1 目标

为发布助手建立统一闭环：

```text
用户描述需求 → 查询事实 → 生成变更草稿 → MCP App 核对
→ 宿主发起继续执行 → HITL 人工批准 → 执行已核对内容 → 展示真实结果
```

必须满足：

1. 用户先看清具体目标、实际参数、差异和影响，再授权执行。
2. 仅核对卡片不执行目标服务变更；未经 HITL 批准不得执行受控写工具。
3. 执行内容与核对、批准内容一致，不能在批准后由模型替换参数。
4. 批准只作用于本次变更，不产生永久放行规则。
5. 刷新、重连、重复点击或多副本处理不得导致重复变更。
6. 前端区分已受理、执行中、成功、失败和结果未知，不把 `deploying` 当作成功。

按当前实现逐条对照（详见 §0.1）：第 2、3、4 条由运行时保证并已实测；第 1 条部分满足——参数可见、差异不可见；第 5 条部分满足——CAS 与前端防重已实现，多副本未实测；第 6 条部分满足——卡片区分待确认/提交中/已提交/结果未知，但不区分工具业务失败（见 §0.5-2）。

### 1.2 本期不包含

- 独立审批人、审批角色、多人会签、审批中心和组织权限系统。
- 一次授权多个服务或一串操作的批量审批。
- 自动回滚、定时发布、灰度发布等新业务能力。
- 平台普通 REST 管理入口统一接入审批。
- 将 MCP App iframe 视为可信授权方，或允许其直接执行平台写操作。
- 修改现有服务发布、环境变量全量覆盖、包引用计数等业务语义。

本期人工审批人是当前会话的操作者。该机制是发布助手操作确认，不等同于新增身份认证或企业级授权系统。不能声称它阻止了直接访问现有 REST/MCP 接口的其他客户端。

| `unpublish_service` | 必须 | 必须 | `ask` | 下线影响及结果 |

| `upload_package` | 不需要 | 不需要 | `allow` | 上传中、校验失败或上传成功 |
| `register_service` | 不需要 | 不需要 | `allow` | 注册中及真实注册结果 |
| 五个现有查询工具 | 不需要 | 不需要 | `allow` | 查询结果或折叠工具行 |
| 新增草稿准备/查询工具 | 用于提供卡片内容 | 不需要 | `allow` | 草稿核对卡 |

现有查询工具包括 `list_images`、`list_packages`、`get_package_detail`、`list_services`、`get_service_status`。

约束：

- 上传成功不代表授权发布；上传后仍必须单独核对并批准 `publish_service`。
- `register_service` 重试不弹审批；失败如实展示，不自动扩大为重新发布。
- 生成、校验、打包、交付本地下载文件不纳入服务变更审批。
- 不把 `upload_package`、`register_service` 放入草稿状态机，不为它们保留隐式对话确认门槛。

## 4. 分层职责

### 4.1 发布助手

负责收集需求、查询事实、生成草稿、说明影响、请求执行和汇报结果。更新提示与 skill 后，应明确禁止绕过草稿流程，但提示词只是行为引导，不能代替运行时校验。

### 4.2 Go 平台后端

负责草稿参数校验、默认值解析、目标快照、有效期、参数冻结、执行认领及结果记录。实际变更继续调用既有 `service.Core`，不另写一套发布实现。

### 4.3 agent-framework

负责会话与工具调用绑定、核对状态的可信记录、HITL 等待与恢复，以及五个受控工具的执行前检查。模型提供的 `confirmed`、UI 文本或 `ui/update-model-context` 不能被直接当作授权凭据。

### 4.4 Next.js 宿主

负责 iframe 隔离、资源加载、卡片生命周期、核对按钮与审批按钮、连续流事件、历史恢复、重复提交保护。最终人工审批按钮由宿主渲染，而非由 iframe 自行授权。

### 4.5 MCP App

负责展示后端提供的草稿内容、差异和影响，发出界面交互请求。不能获取通用平台写权限，不能直接执行五个受控操作，也不能直接执行两个免审批写操作；免审批不意味着 iframe 具有任意写调用权限。

| `get_service_change` | 以草稿标识读取脱敏详情、执行状态和结果；校验会话访问范围 |

准备草稿可以写草稿记录，但不得创建/更新/删除目标服务，不得提前应用 ConfigMap 或 Kubernetes 资源。

Go MCP 通过标准 `resources/read` 返回 UI HTML。工具通过 `_meta.ui.resourceUri` 或 release-agent 的 `ui.tools` 映射关联资源；不要求模型生成 HTML。

### 5.2 草稿字段

拟以平台 MySQL 持久化草稿，复用现有数据访问方式。逻辑字段如下，物理表结构在实施时按项目命名规范落定：

| 字段 | 约束 |
|------|------|
| `proposalId` | 服务端生成的不可预测标识，不作为授权凭据 |
| `operation` | 仅允许五个受控操作 |
| `sessionId` / 调用来源 | 由可信运行时绑定，不能只信任模型传参 |
| 目标标识 | 已有服务使用稳定 `serviceId`，同时保存核对用 `k8sName`；新发布保存包标识及名称意图 |
| 冻结参数 | 解析默认值后的有效参数；实际执行只读取此份参数 |
| `parameterDigest` | 参数一致性摘要；不得在公开摘要中暴露敏感值指纹 |
| 目标快照 | 当前包、镜像、环境配置和影响执行的关键业务状态；不包含易变 Pod 计数等噪声 |
| 脱敏展示内容 | 卡片与审批区共同使用，避免模型另行概括造成遗漏 |
| 创建/过期时间 | 服务端时间，TTL 可配置；过期后必须重新核对 |
| 执行状态 | 准备、执行认领、受理、终态等状态 |
| 执行关联 | 服务标识、工具调用标识、受理时间及结果摘要 |

不能把完整敏感参数写入普通日志、SSE 审批文本或前端历史。草稿若需要保存新密钥，应使用受保护的服务端存储及引用；明文展示 DTO 与执行参数必须分离。

**该约束当前未满足，且被用户明确调整**：本期按「平台可信、不做身份认证与密钥管理」执行，`update_service_env` 已具备实际变更能力，但完整 `env` 仍随 `permission_ask` 进入 SSE 并被历史保存（§0.5-3）。若后续要收窄暴露面，需要另立需求实现展示 DTO 与执行参数分离，不能以现有遮掩按钮充当已保护。

### 5.3 不可变与一致性

- 用户需要修改内容时创建新草稿，旧草稿失效；第一期卡片以核对展示为主，不提供独立复杂配置编辑器。
- 默认镜像在生成草稿时解析并展示，执行时不得重新取可能变化的默认值。
- 展示镜像 tag 不等于保证镜像字节不变；本期不新增镜像 digest 解析能力，不能承诺可变 tag 的内容冻结。
- 重新发布必须明确显示是否换包、换镜像，不能统一描述为“仅重启”。
- 执行前再次校验目标快照。关键配置变化则拒绝旧草稿，要求重新核对和审批。
- 快照校验与写操作之间需要服务级串行化或等效的原子并发控制，不能只做一次查询后无保护地写入。
- 普通 REST 变更虽不纳入审批，但应参与必要的服务写并发控制，避免其在校验与执行间插入变更；该点属于保障一致性的必要内部改造，不是给 REST 加审批。

## 6. 核对、审批与执行契约

> 本节 6.1、6.2、6.4 依赖未实现的草稿/宿主核对登记（`proposalId`、`parameterDigest`、独立准备工具），当前无落点。**已实现并可验证的是 6.3 的 HITL 替代路径**：`ask` → `permission_ask` 暂停 → `POST /threads/{sid}/confirm-stream` 提交 `{tool_call_id, confirmed}` → 运行时从确认上下文取原始 `ToolUseBlock` 恢复；参数由运行时冻结，`confirmed` 只接受布尔 `true` 才批准（见 §0.3-3）。

### 6.1 核对绑定

卡片核对以 `(sessionId, proposalId, parameterDigest)` 绑定。浏览器经宿主发起核对操作，运行时记录核对状态；它不是模型可调用的通用确认工具。

实施需增加宿主专用的核对登记契约，并在现有会话访问边界内校验请求。具体路由与 DTO 在实施时确定，必须满足：

- 不接受其他会话的草稿。
- 不允许过期、取消或参数不一致的草稿被标记核对。
- 不将 iframe 消息里的自报身份作为可信身份。
- 核对不直接调用写工具，不生成永久授权。
- 模型即使提前请求执行，运行时也要拒绝未核对草稿。

该登记与既有 HITL 一样是当前操作者的确认，不证明操作者具有新引入的审批角色。

### 6.2 触发继续执行

用户点击「核对无误，申请执行」后：

1. 宿主登记核对并更新卡片状态。
2. 当前 SSE 未结束时，将一次继续执行请求排队，不重复发送。
3. 宿主发起下一轮，携带草稿引用，请求助手执行该草稿。
4. 静默上下文更新只用于辅助模型感知，不能替代启动下一轮或授权记录。
5. 会话已切换、草稿已失效或组件已卸载时，不再发送排队请求。

使用独立准备工具展示卡片，不依赖受控写工具的 `TOOL_CALL_START` 与 `permission_ask` 的先后顺序。

### 6.3 HITL 授权

- 五个写工具均为 `ask`，运行时发出 `permission_ask` 后暂停。
- 宿主将审批条目关联到同一草稿，显示操作、目标和脱敏摘要。**当前无草稿**：卡片直接展示工具名与完整参数，遮掩仅作用于展示层（§0.5-3）。
- 用户通过 `POST /threads/{sid}/confirm-stream` 提交批准或拒绝。
- 不提供“记住允许”“以后自动批准”等入口；不将本次批准保存为通用允许规则。
- 批准后恢复的必须是原工具调用及其草稿，不能用新参数重建另一项操作。**当前由确认上下文保证**：恢复使用存储的原始 `ToolUseBlock`，无草稿参与。
- 删除名称由宿主校验，与可信目标名一致后才允许提交批准；后端原有 `confirm_k8s_name` 校验继续保留。模型能够复述目标名不等于用户已确认删除。**当前未实现该输入校验**：卡片只展示 `k8sName` 与 `confirm_k8s_name` 供肉眼核对，实际拦截依赖后端参数校验，见 §0.1 与 §0.5-1。
- 拒绝后该执行请求终止，重新发起同类变更需新草稿和新审批。**当前语义**：需新一次 `permission_ask` 和新审批（已实测），无草稿概念。

### 6.4 后端执行接口兼容

保留既有五个写工具及其 Core 实现，新增可绑定草稿的执行路径。发布助手受控路径要求草稿引用，并拒绝混入不同的原始参数。

现有 MCP 客户端直接传原始参数的兼容范围应保持明确：本期不宣称将所有客户端升级为强制审批。发布助手运行时必须限制其模型侧调用为草稿路径，不能通过省略 `proposalId` 回退到旧路径。

运行时与后端各负其责：运行时保证当前助手调用经过核对和 HITL；后端保证草稿参数、状态及幂等。后端不能仅凭 `proposalId` 推断调用者经过了人工审批。

## 7. 状态与故障处理

### 7.1 两类状态分离

| 状态域 | 状态示例 | 权威来源 |
|--------|----------|----------|
| 交互/审批 | 待核对、已核对、待审批、批准提交中、已拒绝 | 运行时持久化确认记录与 `pendingConfirm` |
| 草稿/执行 | prepared、claimed、accepted、succeeded、failed、unknown、expired、cancelled | 平台后端草稿与执行记录 |

前端卡片合并呈现，不维护一份可以独立授权执行的本地状态。不得因前端按钮显示“已批准”就推断后台已经接受执行。

### 7.2 幂等与崩溃窗口

- 执行入口通过数据库条件更新原子认领草稿；并发请求只有一个能进入实际写调用。
- 重复请求返回既有受理信息或状态，不再次创建服务或滚动重启。
- 新发布应持久化草稿到新服务的关联，并以唯一约束防止重试生成第二个服务。
- 不能把“数据库已认领”误认为“外部 Kubernetes 操作成功”。进程在认领后、结果回写前崩溃时，进入待核实/`unknown`，通过已记录目标查询实际状态，不直接重放。
- 若无法确定是否发生副作用，前端明确显示“结果待核实”，阻止自动重试。不得宣称跨数据库与 Kubernetes 已实现无条件 exactly-once。

### 7.3 长操作与结果

- 发布、环境变量更新、重新发布返回 `deploying` 时显示执行中。
- `running`：就绪且注册成功。
- `register_failed`：部署运行但注册失败，展示部分失败；可以直接调用免审批 `register_service` 重试。
- `deploy_failed`：部署失败，展示错误和服务详情入口。
- 下线成功需确认接口结果与服务状态；删除成功使用后端删除结果和执行记录，不能依赖已不存在的服务详情页。
- 轮询有可配置间隔、总时限和错误退避；超时不等于失败，也不触发自动重发写操作。
- 后端执行状态查询应能根据关联服务刷新结果，不能只依赖浏览器一直在线推进状态。

## 8. 各类核对卡内容

> 本节描述原始设计的目标卡片。当前确认卡只展示工具名、`tool_call_id`、`input` JSON 与五个常用字段摘要，**不计算差异、不显示目标快照、不要求输入名称**；8.1/8.3/8.4 的“实际镜像、副本数、现状与目标对比”等断言在实现前不成立。

### 8.1 发布

展示配置包 ID、名称、版本、目标名称、实际镜像、副本数、环境变量键及脱敏值、创建资源和访问入口预期。尚未分配的 serviceId/endpoint 不得伪造，执行后补齐。

### 8.2 环境变量变更

明确显示「全量覆盖，未包含的原有键将被删除，并触发重新部署」。分别列出新增、修改、删除、保留项；保留项可折叠。差异由后端对实际值计算，不能通过脱敏后的 `••••` 比较。

**当前实现**：只有全量覆盖提示，没有差异计算；卡片展示的是本次提交的完整 `env`（默认遮掩值），人工需自行与现状比对。

沿用现有保留键校验、64 键和单值 32KB 等约束，不复制另一套可能漂移的前端规则作为唯一校验。

### 8.3 重新发布

展示目标服务、现状、当前与目标包、当前与目标镜像、复用配置及重新部署影响。无包/镜像变更时明确显示复用当前配置，不误称为版本升级。

### 8.4 下线

展示名称、ID、当前状态、访问地址；说明删除运行资源、停止访问，保留服务记录与配置包，可后续重新发布恢复。

### 8.5 删除

展示稳定目标标识、实际 k8sName、运行资源、数据库记录及包清理条件。配置包仅在无其他引用时清理，不能笼统写“删除所有配置包”。明确不可逆，最终审批区要求输入准确目标名称。

**当前实现**：卡片展示 `k8sName` 与 `confirm_k8s_name` 参数值，无输入框、无不可逆二次确认文案，包清理范围由后端语义决定。

### 8.6 免审批结果

上传只展示文件、校验摘要、packageId 与成功/失败；不展示整段 Base64。注册只展示执行状态、注册信息或失败原因，不添加审批按钮。

### 9.2 事件规则

- 历史恢复使用 `pendingConfirm` 与服务端草稿状态，不重新创建草稿或自动发起执行。
- SSE 重放时利用事件序号及调用标识去重；审批终态不能被迟到的旧事件覆盖。

状态以文本和图标共同表达，不只依赖颜色。常规查询默认折叠，关键变更卡保持可见。桌面与窄屏不横向溢出，键盘可访问按钮与删除输入框，执行失败保留详情而非只弹短暂通知。

## 10. 代理与安全约束

### 10.1 复用现有端点

前端统一使用 `/agent/release-agent` 前缀：

- `POST /threads/chat`：发起一轮对话。
- `POST /threads/{sid}/confirm-stream`：恢复人工确认调用。
- `GET /threads/{sid}/history`：历史及待审批恢复。
- `GET /mcp/platform-publisher/resources/ui?uri=...`：读取卡片资源。
- `POST /mcp/ui-context`：静默更新模型上下文，不代表批准。

Go MCP 实现的是 `resources/read`；`resources/ui` 是运行时 HTTP 代理，两者不能混淆。

### 10.2 Host 限制

- 只加载已声明且允许的 `ui://` 资源，拒绝任意外部 HTML。
- iframe 使用最小 sandbox 和 CSP；校验 `event.source`、握手关联、消息结构及允许的方法。对于 sandbox 产生的 opaque origin，不能仅靠字符串 origin 作为校验。
- 不向 iframe 传递访问令牌、完整密钥或通用平台 API 凭据。
- Host 不将受控写工具调用转发给工具代理，也不通过 `confirmed:true` 重试来替代 HITL。
- 资源失败保留宿主错误与重试入口，不因卡片加载失败降级成“直接执行”。
- 403 等错误保留结构化响应用于正确反馈，不能只抛一个丢失状态的普通字符串错误。

## 12. 验收准备与证据要求

本轮已执行的部分验证见 §0.2；未执行项不能引用之前 approval-forms 的通过结果替代本功能验收。

### 12.1 隔离环境

- 使用专用测试包和有明确标识的测试服务，不操作现有 release-agent 或真实业务服务。
- 执行前记录目标 serviceId/k8sName，删除测试只允许已登记的测试目标。
- 准备正常包、无效包、环境变量变更样本、注册失败及部署失败的受控场景。
- MySQL、Redis Streams、MCP 与 UI 代理可用；另准备断线/重启恢复场景。
- 敏感值仅用专用测试凭据；截图、SSE、日志和报告全部脱敏。
- **被测实例自检（实测踩坑）**：MCP 采用 fail-soft 启动，`/config/AGENTS.md` 缺失或损坏时实例照常运行但注册 0 个平台工具，助手会声称“没有该工具”而不报错。开始用例前必须确认日志出现 `MCP: 1 - [platform-publisher]` 与 `Recorded 12 MCP tools`。
- **包配置写入自检**：向 PVC 包目录写配置必须校验字节数与哈希后再重启；本轮曾因重定向写法把 `AGENTS.md` 写成 0 字节，导致工具全部消失。判断确认是否启用还要核对 `permission.mode: default` 与 `permissions.tools.*` 的具体值——`read_only: true`/`mode: bypass` 会让受控工具直接执行（§0.3-1）。

### 12.2 证据

每项记录：用例编号、代码版本、测试时间、执行方式、前置数据、操作、实际结果、是否通过、截图/日志位置。未执行标为「未执行」，受环境限制标为「阻塞」，不得写成通过。

仅截图出现审批卡不足以证明拦截有效。必须结合写调用计数、后端执行记录或目标资源变化，证明批准前零副作用、批准后仅一次执行。

**本轮证据的边界**：只采集了浏览器 DOM/SSE、确认请求体、历史接口响应与截图，没有写调用计数、后端执行记录或真实资源 diff，因此该要求未满足；截图的视觉复核也因模型无法读取图像而未完成（§0.2）。

## 13. 功能验收与自动化方案

### 13.1 自动化分层与验收口径

功能验收以自动化 **e2e 为唯一验收判定层**：F01–F17 与适用的 C 用例必须在 L3/L4 上实际执行并全部通过，人工只做抽查与结果复核。L1/L2 单测是实施期回归门槛与快速反馈，不作为 F/C 用例的验收证据层。

| 层 | 形态 | 职责 | 依托 |
|----|------|------|------|
| L1 | Go 后端单测（`go test`，fake K8s 客户端/内存库） | 支撑：草稿校验、差异计算、原子认领、幂等的快速回归 | 参照 `backend/internal/service/publish_test.go` 既有模式 |
| L2 | 运行时测试（agent-framework `mvn test`） | 支撑：五个 `ask` 拦截、免审批直执行、未核对草稿拒绝的快速回归 | 参照 ChatStreamControllerTest / McpToolRegistrar 既有测试 |
| L3 | API 级 **e2e 验收**（脚本直连 SSE/REST/MCP 代理，无浏览器） | 验收：对话闭环、`confirm-stream` 批准/拒绝、事件序列与集群/数据库副作用断言 | 复用 approval-forms e2e 的 SSE 截获与流结束等待手法 |
| L4 | 浏览器 **e2e 验收**（Puppeteer + 截图） | 验收：卡片挂载、按钮生命周期、排队发送、刷新恢复、窄屏与键盘操作 | 复用 `approval-e2e.js` 骨架与截图核对方法 |

口径：单测失败一票否决（不得进入 e2e 阶段），但单测通过不等于验收通过；验收结论只认 e2e 结果与集群/数据库证据。

CI 归属：L1、L2 进现有 GitHub Actions 工作流作为合并门槛；L3、L4 依赖 kind 集群与浏览器，作为验收执行层在本地或自托管 runner 运行并归档报告，不改造现有三工作流的触发范围。

### 13.2 测试环境、替身与故障注入

- 集群与目标：现有 kind + `agent-platform` 命名空间；测试目标统一前缀 `hitl-e2e-`，用例自建自清理，断言只读（`kubectl get` / SQL SELECT）。
- 被测组件全部用真实实现：Go 后端（含草稿与执行）、agent-framework、MCP 资源与工具代理、前端构建产物；不 mock 被测对象本身。
- LLM 用专用测试凭据按固定剧本推进（用户输入固定）；断言锚定平台状态机、草稿状态轨迹、K8s 资源与数据库记录、SSE 事件序列，不锚定模型措辞。
- 故障注入优先走真实路径：非法包内容触发 F03；不存在的镜像 tag 触发 `deploy_failed`；错误 A2A 地址触发 `register_failed`。仅「长时间停留 deploying」允许后端测试开关，且只对 `hitl-e2e-` 前缀目标生效。
- 证据采集：每场景前后集群快照（Deployment/Service/Ingress/ConfigMap）、服务与草稿表行数、`sess:{sid}:events` 事件导出、SSE 录制、脱敏截图，随报告归档。

### 13.5 执行与产物

- 每个场景独立可重跑：前置自检（依赖、凭据、基线快照）失败即标阻塞，不产出误导性结果。
- L3/L4 需连续 3 次全绿方计入通过；仅基础设施类故障允许重跑，业务断言失败不得靠重跑掩盖。
- 拟在 `e2e/release-agent-hitl/` 新增浏览器驱动、API 场景、只读证据采集和 fixtures；复用仓库 Puppeteer 依赖。此目录与执行入口目前尚未实现，不提供虚构的可执行命令。
- **本轮的执行入口不是该目录**：由 Playwright MCP 手工驱动真实页面，产物是截图、SSE 录制与只读 HTTP 断言（记录见 §0.2/§0.2.1 及 `e2e/screenshots/`）；因不是脚本化用例，不能重复运行，也不能据此计入「连续 3 次全绿」。
- 每次执行按 runId 输出 `report.json`、可读摘要、逐用例脱敏截图、SSE 记录与资源差异。报告逐项包含用例编号、期望/实际结果、证据路径、耗时和通过/失败/阻塞状态；任一失败或阻塞不得返回“全通过”。
- 每项交互等待明确状态或事件并设置超时，不使用固定 sleep 判断完成。收到 `permission_ask` 后先采集批准前证据，再由浏览器点击批准或拒绝，最后采集执行证据。
- 快照只比较登记测试目标的业务相关字段，排除时间戳、resourceVersion 等自然变化。环境变量需检查 ConfigMap 内容与 Deployment 的 envFrom 引用，而非仅比较 Deployment 内联 env。
- 清理前校验本次 runId、资源 UID 与创建清单，不按名称前缀批量删除；失败先保留脱敏证据，清理结果单独报告，不触碰共享业务数据。

## 16. 实施顺序、上线与回退预案

### 16.1 实施顺序

1. 明确草稿 DTO、可信核对登记、敏感参数保存和服务级并发控制接口。
2. 实现后端草稿、UI 资源和执行绑定，完成约束测试。

4. 接入前端 Host、审批区、状态恢复和事件处理。
5. 更新 release-agent 配置及提示，执行隔离环境全量验收。

### 16.2 上线约束

- 数据变更采用增量方式，保留现有业务数据；不执行破坏性表重建。
- 后端、运行时、前端和 release-agent 包版本作为一组记录；先确保依赖能力可用，再启用新助手流程。
- 混合版本或缺少能力时，五个受控操作应停止并提示能力不匹配，不能降级为 bypass。
- 待审批草稿绑定生成时版本/契约，升级不兼容时失效并重新核对。
- 部署和服务重启另行按项目流程执行，本文件不包含已执行部署记录。
- **本轮已执行的部署（与上述原则的偏差，需后续纳入正式流程）**：直接替换了集群镜像并修改了 PVC 包内配置，未走平台重新发布，也未同步清单；`kind load` 导入的本地镜像要求 `imagePullPolicy: IfNotPresent`，否则 Pod 会 `ImagePullBackOff`。平台重新发布 release-agent 会用包内容覆盖这些改动。

### 16.3 回退原则

- 出现安全或一致性缺陷时先禁用助手受控写操作，保留查询，不恢复旧的无确认执行作为安全回退。
- 已受理任务继续查询真实结果；撤销待审批或未受理草稿不等于撤销已执行业务变更。
- 保留草稿及执行记录用于核查，不删除数据库或 Kubernetes 资源来“清理回退”。
- 如需回退组件版本，先核对增量数据兼容性；不自动撤销服务环境变量、镜像或配置包。

## 18. 已知通道限制（2026-09-18 补录，实测复现）

- **A2A（message/send）通道不支持 ask 工具**：五个变更工具的挂起态只存于 harness checkpoint（`HarnessAgentRunner` 直调 `agent.stream()`，不经过 `AgentRuntimeService.forwardEvent` 的 `putConfirmContext`），平台 confirm_context 无记录，`confirm-stream` 无法恢复；且 A2A 会话共享 `{userId}:unknown` 键（SDK 未传 sessionId/taskId），挂起后同会话后续请求持续 `IllegalStateException`（会话锁死）。该限制已声明于注册卡 description（`AgentCardNotes.A2A_CHANNEL_LIMITATION`，覆盖 `/.well-known/agent-card.json` 与 A2A Server 卡片）及 agent-framework AGENTS.md §4；变更类操作必须走 `/threads/chat` + `/threads/{sid}/confirm-stream`。本设计未覆盖 A2A 对话通道，A2A 接入确认流另立设计。
- **confirm-stream 恢复 turn 的沙箱竞态（沙箱开启时）**：挂起 turn 的 harness flux 在 AGENT_END 之后才真正 complete，其收尾 `OpenSandbox.stop()` 会关闭恢复 turn 刚连接的沙箱。日志链（release-agent 18:12:08-09）：`permission_ask`（08.695）→ 恢复启动（08.752）→ 恢复连接沙箱成功（08.874）→ 旧 turn flux 完成 `POST_CALL ended on a tool-call turn`（09.072）→ `stop() called`（09.073）→ 恢复 turn 文件系统 404（09.100）→ `SandboxConfigurationException: No active sandbox — sandbox filesystem used outside of a call context`（09.121）。恢复失败后 ASKING 态残留，同会话后续请求报 `IllegalStateException ... supplied no confirmation`（会话锁死）。与 8e9f61b 修复的"迟到收尾关掉下一轮 sink"同族，但位于 harness 沙箱生命周期层，控制器层 `turnEnded` 保护不可达。沙箱关闭（`SANDBOX_ENABLED=false`，应用默认）的部署不受影响。
